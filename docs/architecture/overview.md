# アーキテクチャ概要

横断的な技術決定を「決定 / 背景 / 棄却した選択肢」の 3 項でまとめる。バージョン番号や依存ライブラリ一覧は記述しない（`package.json` を参照）。

## 1. フレームワーク: React Router v7 (SSR モード)

- **決定**: フロント・バックを単一アプリで賄う React Router v7 の SSR モードを採用する。`loader` / `action` でデータ取得・更新も同居させる。
- **背景**: アカウント不要・URL 共有が中核ユースケースであり、共有 URL の OGP・初期表示速度・SEO 適性のため SSR が有利。フロントとサーバーで型を共有でき、ルートごとに loader 戻り値の型が `useLoaderData<typeof loader>()` で推論されるため、API スキーマ管理のコストが消える。
- **棄却した選択肢**:
  - **Next.js**: 採用候補だが、本アプリ規模では React Router v7 のシンプルさで十分。
  - **SPA + 独立 API サーバー（Express）**: 以前はこの構成を試したが、フロント↔ API の型重複が発生し、デプロイ単位が増えるためやめた。

## 2. データベース: SQLite + Prisma + libSQL Driver Adapter

- **決定**: SQLite を Prisma 経由で扱う。本番では libSQL ドライバアダプタを通すことで Turso 等のリモート SQLite にも繋げる構成にする。
- **背景**: グループあたりの規模が小さく、書き込み頻度も高くないアプリ特性に SQLite が合う。Prisma により型安全なクエリと宣言的マイグレーションが手に入る。
- **棄却した選択肢**:
  - **PostgreSQL**: 当面は過剰。アカウント概念がなく接続数も少ない。
  - **生 SQL + better-sqlite3**: 型と migration の運用負担が増える。

## 3. UI: HeroUI + Lucide React + Tailwind CSS

- **決定**: メイン UI コンポーネントは HeroUI、アイコンは Lucide React、スタイリングは Tailwind CSS を組み合わせる。
- **背景**: モダンで洗練された見た目を最小コストで成立させたい。HeroUI は React 19 / Tailwind v4 系と親和性が高く、独自コンポーネント実装の必要性を下げる。
- **棄却した選択肢**:
  - **完全自作 + Tailwind のみ**: 一貫性とスピードが落ちる。
  - **MUI / shadcn-ui**: トーンや React 19 対応の判断が当時の HeroUI ほど合致しなかった。

## 4. 認証なしモデル

- **決定**: アカウント・ログインを設けず、グループ ID（8 文字英数字）を知る者がそのグループの編集権を持つ。
- **背景**: 家族・恋人など極めて狭いクローズドな共有を主用途とし、登録のハードルを排して使い始めの摩擦をゼロにする方針。
- **棄却した選択肢**:
  - **メール / OAuth 認証**: 登録が必要になり、本アプリの「URL 一本で共有」というコア体験が損なわれる。
  - **読み取り URL と編集 URL の分離**: 将来検討余地はあるが、現状の共有規模では UI が複雑化するデメリットが上回る。
- **トレードオフ**: グループ ID がコピー漏洩すると編集権が奪取される。これは仕様として受容し、ID の不可推測性（8 文字 36 進）を担保する。検索インデックス可能な導線（公開リスト等）は持たない。

## 5. URL メタデータ取得: Cheerio によるサーバーサイドスクレイピング

- **決定**: URL 登録時にサーバー側で対象 URL を fetch し、Cheerio で OGP / meta を抽出する。
- **背景**: クライアントから直接取得すると CORS で頻繁に失敗する。サーバーサイドでまとめて取得し、結果を Bookmark の `auto*` フィールドに保存することで、サイト側の変更からユーザーの手入力値を守る。
- **棄却した選択肢**:
  - **外部のメタデータ取得 SaaS**: 依存とコストが増える。
  - **クライアントサイド取得**: CORS で実用にならない。
